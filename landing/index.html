01 / binding

It installs like any other binding.

chardb is a Worker binding. One npm install, one entry in wrangler.jsonc, and your database is in scope next to KV, R2, and D1.

· 
{
  "chardb": [{ "binding": "DB", "schema": "./src/schema.ts" }]
}
[[chardb]]
binding = "DB"
schema  = "./src/schema.ts"
worker.ts 
import { client } from "chardb";
import { eq } from "drizzle-orm";
import { messages } from "./schema";

const db = client(env.DB);
const rows = await db.select().from(messages).where(eq(messages.channelId, id));
bind it. import it. query it.

02 / scale

Scale up to ~160 TB without changing a line.

chardb auto-reshards as your data grows. No 10 GB cap, no manual split, no second provider for the data that actually matters.

  • 16,384 vshards, range-routed
  • reshards online, no app pause
  • one bill, not two providers
scale isn't a migration.

03 / tenancy

Sharded the way your app already works.

Per-tenant ACID, declared in the schema. forOrg(), forUser(), and globalScope() from chardb/server mark the boundary; chardb routes every query and transaction by it.

schema.ts 
import { forOrg } from "chardb/server";
const { cdbTable } = forOrg();

export const messages = cdbTable("messages", {
  id: text("id").primaryKey(),
  // shard key — you already wrote it.
  organizationId: text("organization_id").notNull()
    .references(() => auth.organization.id),
  body: text("body").notNull(),
});
the schema is the boundary.

04 / auth

Auth and data, one schema.

Auth tables live in the same schema, the same client, the same query layer. Roles, permissions, and column-level access compile down with the rest of your types.

  • better-auth under the hood
  • roles and column masks in the schema
  • one query layer, not three services
schema.ts 
export const messages = cdbTable(
    "messages",
    {
        id: text("id").primaryKey(),
        channelId: text("channel_id")
            .notNull()
            .references(() => channels.id, { onDelete: "cascade" }),
        organizationId: text("organization_id")
            .notNull()
            .references(() => auth.organization.id, { onDelete: "cascade" }),
        authorId: text("author_id")
            .notNull()
            .references(() => auth.user.id, { onDelete: "cascade" }),
        body: text("body").notNull(),
        createdAt: integer("created_at").notNull(),
    },
    {
        // `self` appears under `roles:` below, so chardb requires an
        // explicit binding to the user-FK column. Validated at boot.
        selfBy: "authorId",
        roles: {
            admin: "*",
            member: {
                read: "*",
                create: ["body", "channelId"],
            },
            self: {
                read: "*",
                update: ["body"],
                delete: true,
            },
        },
    }
);

row + column policies live with the column. validated at boot.

users are just another table.

05 / files

Files are columns.

file() and fileArray() are first-class Drizzle column types. Stored on R2 in your account, validated with zod / typebox / valibot at the edge, queried alongside the rest of your data.

  • upload, validate, store — one column type
  • R2 in your Cloudflare account, no third party
  • row-level access policies apply to attachments too
schema.ts 
import { file, fileArray } from "chardb/files";

export const messages = cdbTable("messages", {
  id: text("id").primaryKey(),
  body: text("body").notNull(),
  attachment: file({ maxBytes: 25 * 1024 * 1024 }),
  images: fileArray({ mime: "image/*" }),
});
no upload endpoint to write.
