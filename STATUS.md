# Chardb status

Chardb is an experimental architecture prototype. Its package and generated scaffold can be built and inspected, but it is not ready for production data. A narrow organization mutation and live-query path works through configured Durable Objects under workerd. The clean-tarball smoke now sends one live replacement to two independent same-organization browser connections before its persistent restart, mutation replay, and cross-organization denial checks. Schema upgrades, exact resume replay, and several failure boundaries remain unfinished.

This status reflects the code in the repository, not the broader product described by older comments or generated examples.

## Status definitions

| Label | Meaning |
| --- | --- |
| Implemented | Code exists and its normal local path is exercised by tests. |
| Isolated | The component is exercised with pure helpers, a fake client, or a focused workerd worker, but not through a deployed Chardb application. |
| Partial | Some runtime pieces exist, but a required step or safety check is absent. |
| Missing | The advertised behavior has no working runtime path. |

The committed trust boundary is deliberately narrow. Gateway sends `welcome` and stores a verified attachment only after JWT verification. It stores the subject and time bounds, not tenant, role, or custom claims. Declared organization mutations, initial queries, and dirty live-query reruns use the subject plus their validated partition key to ask Catalog for current membership, role, roles, and auth epochs. The Catalog read is the authorization linearization point. Revocation blocks the next dispatch or rerun but does not cancel a shard call that was already authorized. Undeclared operations, mismatched, scatter, and cross-partition queries, and presence remain closed.

## Packed application proof

The clean-tarball smoke now proves this packed sequence:

1. install chardb 0.1.0 from a clean tarball and build the chat client with both stable refs;
2. complete Better Auth anonymous sign-in and select the idempotently created demo organization;
3. open the configured Gateway under workerd with the issued JWT;
4. receive and acknowledge an empty initial query snapshot;
5. run `postMessage` and receive and acknowledge the live replacement;
6. close the socket, dispose Miniflare, and restart the identical packed Worker over the same Durable Object directory;
7. verify the original user, session id, and active organization before any new sign-in, then issue a fresh JWT for the restarted origin;
8. reconnect with the same client id, replay the exact prior mutation, require the identical result, and read exactly one persisted row;
9. sign in a second principal, move it to another organization, deny its query against `demo-org`, and return an empty snapshot for its own organization.

It does not replay an exact missed snapshot from a resume cookie or migrate existing storage. The passing smoke establishes one application slice, not production readiness.

## Verification state

CI runs the strict TypeScript check, repository-wide Biome check, package and landing builds, packed-package import checks, generated-project checks, and the packed chat typecheck and build. The tarball is limited to `dist`, the license, and public documentation.

CI uses one correctness runner. It runs ordinary tests together, then starts each Miniflare workerd harness in its own process to avoid shared-port collisions. Timeout and cancellation handling terminates the whole harness process group before the runner exits. After the package and generated-project smokes, CI runs `scripts/smoke-packed-chat.mjs` against the clean tarball. Focused harnesses and one packed smoke do not replace versioned migrations, exact resume replay, and broader failure tests.

The configured `gateway-live` harness includes default-small, environment-scalable SDK scenarios for two-tenant mutation fanout and selective subscription refresh. They check exact tenant and filter results, durable version convergence, drained invalidation outboxes, and cleanup. The fanout case converges half the writes, replaces half the clients, rematerializes their exact tenant rows, then completes the remaining writes. It also drops up to one batch of committed SDK mutation responses. The test holds each replacement before `hello`, records one domain row, op-log row, and clock step for the first attempt, then releases the same pending mutation and requires an identical result under the same `mutId` without another durable change. Each selective-refresh sample reconstructs Cdb while all subscriptions are active, verifies exact registration identity and unchanged Gateway state, closes and recreates the SDK connection, proves exact new Gateway-to-Cdb registration matching, and performs the workload through the recovered topology. Both scenarios require one domain row, one op-log row, and one change-clock advance per first successful mutation. Churn, reconstruction, and replay must not change those counters. `bun run bench:live` runs frozen `ci-smoke`, `client-max-accepted`, or `throughput` profiles. It parses 1 to 20 sequential samples but rejects combinations that exceed the conservative 110-minute benchmark allowance inside the 120-minute manual job. The output directory must be absent or empty. `run.json` records running, completed, or failed status before and during execution. Each sample retains stdout and stderr and produces two `chardb.scale.sample.v1` records. The aggregate `chardb.scale.report.v1` file records the workload, Git revision, Bun and machine metadata, plus min, p50, p95, max, and mean for timing and rate fields. The manual workflow uploads the whole result directory for 14 days. Neither CI nor the manual workflow defines a latency or throughput target, and local Miniflare results are not production performance claims.

A real local-workerd compatibility run requires a host that permits local listeners. The current compatibility counts are `gateway-live` 7/7, `gateway-jwt` 22/22, and `gateway-snapshot` 4/4. The snapshot recovery cases have explicit 15-second budgets. That budget is test infrastructure allowance, not a product latency target. The JWT suite now proves protocol mismatch precedes JWT and JWKS verification. Earlier sandbox failures while binding an ephemeral listener at port 0 occurred before application behavior and are environmental, not evidence for or against production readiness.

A three-sample clean-HEAD local `throughput` run at `2c936fe` on Bun 1.2.22 and an Apple M4 Pro executed 6,144 fanout mutations, 96 response-loss mutations, and 768 selective mutations. The 7,008 first commits produced exact deltas of 7,008 domain rows, 7,008 op-log rows, and 7,008 change-clock steps. All 96 lost responses replayed with the same mutation id and exact stored result while those counters stayed fixed and no duplicate row appeared. The run replaced 24 live clients midway, verified 86,016 logical row deliveries, reconstructed 96 live Cdb registrations across three evictions, and replaced them with 96 exact new SDK/Gateway registrations. Per-sample fanout throughput ranged from 158.65 to 163.89 mutations/s, client churn took 176.87 to 184.77 ms for eight clients, logical delivery throughput ranged from 29,880.85 to 32,929.17 rows/s, response-loss recovery ranged from 3.61 to 3.68 replays/s, selective recovery took 253.94 to 263.18 ms for 32 registrations, writes ranged from 291.60 to 303.20/s, and materializations from 270.62 to 281.68/s. This Miniflare run is regression telemetry, not a benchmark baseline, capacity claim, or performance target.
