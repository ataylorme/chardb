# Chardb status

Chardb is an experimental architecture prototype. Its package and generated scaffold can be built and inspected, but it is not ready for production data. A narrow organization mutation and live-query path works through configured Durable Objects under workerd. A clean-tarball smoke also proves same-`mutId` replay and denial between two principals in different organizations. Schema upgrades, resume replay, and several failure boundaries remain unfinished.

This status reflects the code in the repository, not the broader product described by older comments or generated examples.

## Status definitions

| Label | Meaning |
| --- | --- |
| Implemented | Code exists and its normal local path is exercised by tests. |
| Isolated | The component is exercised with pure helpers, a fake client, or a focused workerd worker, but not through a deployed Chardb application. |
| Partial | Some runtime pieces exist, but a required step or safety check is absent. |
| Missing | The advertised behavior has no working runtime path. |

It counts durable heads after restart, admits same-key replacements without another slot, denies duplicate pending races, and rejects excess before routing, Catalog, Cdb, or installation. The client keeps at most 64 active subscription records and rejects excess synchronously before id allocation, state change, or send. A same-cookie snapshot is re-acknowledged and ignored before sizing. Independent mutation-argument and write-volume bounds, the same-subscription duplicate replacement chain, durable total bytes, presence state, other queues, slow-consumer backpressure, and retention watermarks remain incomplete. |

It validates refs before admission. A valid 33rd request rejects immediately with retryable `CDB_RATE_LIMITED` before UUID allocation, timer creation, map insertion, or send. `mutationTimeoutMs` defaults to 60 seconds and covers reconnect time without resetting. Reconnect resends each record with its original `mutId` and deadline. Success, typed failure, timeout, synchronous send failure, client close, and session failure remove the record and release capacity. React forwards the option. No public retry handle or automatic retry policy exists. |

| Atomic domain transaction core | Isolated | Focused workerd tests cover commit, replay, rollback, and policy-wrapper failures inside Cdb. A raw escape attempted after typed SQL rolls back that SQL and the provisional op-log row. Mutation results accept the exact 512 KiB serialized JSON boundary. The executor rejects larger results with `CDB_INVARIANT` inside the transaction before op-log finalization or the write-set hook, so a fresh overflow rolls back domain SQL and the provisional row. An oversized legacy replay runs neither handler nor hook and leaves its stored row unchanged. Accepted replay behavior is unchanged. The public organization mutation path reaches the same executor after Gateway and Catalog authorization. |

| Public organization mutation | Isolated | A mutation with an explicit stable `ref` and `authority: "organization"` crosses a configured workerd WebSocket, Gateway, Catalog membership lookup, Catalog routing, Cdb policy wrapper, and atomic op-log executor. Gateway validates and transforms raw arguments once before partition extraction, keeps only the verified JWT subject, and builds `ctx.auth` from Catalog membership, role, roles, and auth epochs. Cdb treats the request as a trusted post-validation internal seam and invokes the validated handler without re-transforming arguments. The packed chat smoke reaches this path after actual Better Auth anonymous sign-in and proves that replaying the same `mutId` returns the same result without inserting another row. Mutations without an authority declaration stay closed with `CDB_AUTH_NOT_BOUND`. |
| Query registration | Isolated | For an explicit stable-ref query with `authority: "organization"` that resolves to one exact partition, Gateway persists a unique generation and physical Cdb identity before `Cdb.subscribe`. Gateway and Cdb persist the same static digest of the declared tables' row and column policy metadata and include it in query identity. They do not hash arbitrary function source. Gateway checks the digest before dirty reruns and staged snapshot sends, while Cdb checks it before registered execution. Policy drift retires the generation with `CDB_INVARIANT`; legacy registrations without a digest retire during bootstrap. A quiet registration detects drift on its next work trigger. Cancellation, replacement, unsubscribe, disconnect, and auth refresh also retire exact generations. Gateway commits retirement and its cleanup alarm in one transaction. If close-time retirement fails, a separate best-effort alarm scans durable rowid pages of 32. It preserves exact current verified socket identities, retires missing, stale, or mismatched attachments, and runs exact Cdb cleanup without resetting an in-progress cursor. If both transactions fail, a quiet abandoned head can persist until another event or bootstrap. Public scatter, cross-partition, and general query shapes remain closed. |
| Shard-local query execution | Isolated | `Cdb.queryRegistered` requires the exact active generation, fresh principal and organization authority, and unchanged query identity. It supplies a read-only policy-wrapped Drizzle database, executes the validated handler, and validates the JSON result. Full-row `cdbTable` selects apply row predicates and readable-column masks. Live queries record tables at `FROM` construction and in tracked predicates or ordering, then compare them with the declared table intent. Each terminal execution records its actual typed predicate with the policy floor, and each declared interval bundle's union must contain every observed range for its table and index. Direct and registered results accept up to 4,096 top-level rows and the exact 512 KiB serialized JSON boundary. Registered execution checks the limit after its final generation fence. An excess result returns `CDB_INVARIANT` with guidance to limit or paginate it. Raw or untracked predicates, embedded subqueries, and callback predicates or ordering fail closed. Projections, joins, grouping, and richer query shapes remain closed. |
| Initial query delivery | Isolated | A configured workerd WebSocket test sends exact-partition organization queries from two org-A clients and one org-B client through Gateway validation, Catalog membership and routing, durable registration, Cdb execution, and protocol-v3 snapshots. The clients acknowledge the snapshots. Org B receives an empty array under policy. Other-tenant, undeclared, mismatched, scatter, and cross-partition requests fail closed in focused coverage. |
| Live query update | Isolated | A public organization mutation advances the Cdb change clock and writes matching invalidations into a durable outbox in the same transaction as domain SQL and the op-log. Cdb drains that outbox to Gateway. Gateway durably coalesces dirtiness, reruns each exact registered query with current Catalog authority, stages an immutable replacement snapshot, retries delivery, and advances delivery only on the exact client acknowledgement. A long-lived-socket workerd test changes one membership from `member` to `viewer`, restores `member`, then deletes it. Dirty reruns return an empty snapshot after the downgrade, restore rows after the role returns, and retire the registration with `CDB_FORBIDDEN` after deletion. This is full-snapshot replacement, not row patches or a general live-query engine. |
| WebSocket reconnect, cookies, and auth refresh | Isolated | The client acknowledges new snapshots and re-acknowledges same-cookie retries without applying rows twice. A workerd test evicts Gateway and Cdb while a hibernated socket has a staged replacement. Both objects reconstruct their stored state, Gateway delivers the same staged cookie, and the client acknowledges it. A separate reconnect creates a fresh subscription that reads current state. | Better-auth adapter | Partial | All synthesized auth models use singleton Catalog storage, and Cdb no longer stores or indexes auth rows. | Gateway JWT identity and organization authority | Implemented | Configured Gateway `hello` and `updateAuth` verify real signatures, subject, expiry, not-before, issuer, audience, and allowed algorithms through the Catalog-owned, URL-scoped JWK resolver. Each connection admits only one of those authentication operations at a time. A duplicate receives retryable `CDB_RATE_LIMITED` before verification, Catalog access, attachment mutation, or refresh chaining, and only the exact owner can release its claim on success, rejection, or throw. Catalog enforces a 5-second fetch and read deadline, 256 KiB document limit, 32-key limit, 256-byte `kid` limit, and 2,048-byte URL limit. It coordinates refresh with a durable 10-second lease, caches absent keys for 5 seconds after success, and persists failure cooldown from 1 to 60 seconds. It returns no stale key, ignores the unscoped legacy cache, and retires keys absent from a successful replacement. The attachment stores no tenant, role, or custom claims. Subjectless queries remain closed. Better Auth anonymous accounts become authenticated principals after JWT issuance and organization membership. For each declared organization mutation, initial query, or dirty live-query rerun, Catalog re-derives organization authority from the verified subject. Only `/ws` and `/_chardb/*` are reserved Chardb routes. `/api/auth/*` is mounted when Better Auth is configured. Removed placeholder paths such as `/q`, `/f`, `/p`, and `/s` fall through to the application. React exports no placeholder presence, upload, stream, or vector hooks.

The committed trust boundary is deliberately narrow. Gateway sends `welcome` and stores a verified attachment only after JWT verification. It stores the subject and time bounds, not tenant, role, or custom claims. Declared organization mutations, initial queries, and dirty live-query reruns use the subject plus their validated partition key to ask Catalog for current membership, role, roles, and auth epochs. The Catalog read is the authorization linearization point. Revocation blocks the next dispatch or rerun but does not cancel a shard call that was already authorized. Undeclared operations, mismatched, scatter, and cross-partition queries, and presence remain closed.

## Packed application proof

The clean-tarball smoke now proves this packed sequence:

1. install chardb 0.1.0 from a clean tarball and build the chat client with both stable refs;
2. complete Better Auth anonymous sign-in and select the idempotently created demo organization;
3. open the configured Gateway under workerd with the issued JWT;
4. receive and acknowledge an empty initial query snapshot;
5. run `postMessage`, receive and acknowledge the live replacement, replay the same `mutId`, and read exactly one persisted row through a second subscription;
6. sign in a second principal, move it to another organization, deny its query against `demo-org`, and return an empty snapshot for its own organization.

It does not restart the Worker or Durable Objects, replay missed changes from a resume cookie, or migrate existing storage. The passing smoke establishes one application slice, not production readiness.

## Verification state

CI runs the strict TypeScript check, repository-wide Biome check, package and landing builds, packed-package import checks, generated-project checks, and the packed chat typecheck and build. The tarball is limited to `dist`, the license, and public documentation.

CI runs ordinary tests together and starts each Miniflare workerd harness in its own process to avoid shared-port collisions. After the package and generated-project smokes, CI runs `scripts/smoke-packed-chat.mjs` against the clean tarball. Focused harnesses and one packed smoke do not replace versioned migrations, resume replay, and broader failure tests.
