# Chardb status

Chardb is an experimental architecture prototype. Its package and generated scaffold can be built and inspected, but it is not ready for production data. A narrow organization mutation and live-query path works through configured Durable Objects under workerd. The same package now exposes a typed native `env.DB` entrypoint for registered organization queries and mutations. The clean-tarball smoke applies its packaged migration, exercises both binding methods, sends live replacements to two independent same-organization browser connections, then performs persistent restart, mutation replay, and cross-organization denial checks. Forward maintenance-mode schema upgrades and bounded exact replacement-socket snapshot replay are implemented; online migration traffic, down migrations, and several failure boundaries remain unfinished.

This status reflects the code in the repository, not the broader product described by older comments or generated examples.

## Status definitions

| Label | Meaning |
| --- | --- |
| Implemented | Code exists and its normal local path is exercised by tests. |
| Isolated | The component is exercised with pure helpers, a fake client, or a focused workerd worker, but not through a deployed Chardb application. |
| Partial | Some runtime pieces exist, but a required step or safety check is absent. |
| Missing | The advertised behavior has no working runtime path. |

The committed trust boundary is deliberately narrow. Gateway sends `welcome` and stores a verified attachment only after JWT verification. It stores the subject and time bounds, not tenant, role, or custom claims. Declared organization mutations, initial queries, and dirty live-query reruns use the subject plus their validated partition key to ask Catalog for current membership, role, roles, and auth epochs. The Catalog read is the authorization linearization point. Revocation blocks the next dispatch or rerun but does not cancel a shard call that was already authorized. ## Verification state

CI runs the strict TypeScript check, repository-wide Biome check, package and landing builds, packed-package import checks, generated-project checks, and the packed chat typecheck and build. The tarball is limited to `dist`, the license, and public documentation.

CI uses one correctness runner. It runs ordinary tests together, then starts each Miniflare workerd harness in its own process to avoid shared-port collisions. Timeout and cancellation handling terminates the whole harness process group before the runner exits. After the package and generated-project smokes, CI runs `scripts/smoke-packed-chat.mjs` against the clean tarball. Focused harnesses and one packed smoke do not replace broader failure tests.

The configured `gateway-live` harness includes default-small, environment-scalable SDK scenarios for two-tenant mutation fanout and selective subscription refresh. They check exact tenant and filter results, durable version convergence, drained invalidation outboxes, and cleanup. The fanout case converges half the writes, replaces half the clients, rematerializes their exact tenant rows, then completes the remaining writes. It also drops up to one batch of committed SDK mutation responses. The test holds each replacement before `hello`, records one domain row, op-log row, and clock step for the first attempt, then releases the same pending mutation and requires an identical result under the same `mutId` without another durable change. Each selective-refresh sample reconstructs Cdb while all subscriptions are active, verifies exact registration identity and unchanged Gateway state, closes and recreates the SDK connection, proves exact new Gateway-to-Cdb registration matching, and performs the workload through the recovered topology. Both scenarios require one domain row, one op-log row, and one change-clock advance per first successful mutation. Churn, reconstruction, and replay must not change those counters. `bun run bench:live` runs frozen `ci-smoke`, `client-max-accepted`, or `throughput` profiles. It parses 1 to 20 sequential samples but rejects combinations that exceed the conservative 110-minute benchmark allowance inside the 120-minute manual job. The output directory must be absent or empty. `run.json` records running, completed, or failed status before and during execution. Each sample retains stdout and stderr and produces two `chardb.scale.sample.v1` records. The aggregate `chardb.scale.report.v1` file records the workload, Git revision, Bun and machine metadata, plus min, p50, p95, max, and mean for timing and rate fields. The manual workflow uploads the whole result directory for 14 days. Neither CI nor the manual workflow defines a latency or throughput target, and local Miniflare results are not production performance claims.

A real local-workerd compatibility run requires a host that permits local listeners. The current compatibility counts are `gateway-live` 7/7, `gateway-jwt` 22/22, and `gateway-snapshot` 6/6. The snapshot cases include exact replacement-socket replay, unknown-cookie fallback, and slow-ack coalescing behind one staged outbox row under explicit 15-second budgets.
