The generated app uses four same-Worker Durable Object bindings and one R2 bucket. Application code talks to the exported `DB` binding; Chardb uses the four namespaces internally.

{/* contract: ../docs-examples/generated-app/wrangler.toml */}
```toml wrangler.toml
name = "my-chardb-app"
main = "src/worker.ts"
compatibility_date = "2026-05-10"
compatibility_flags = ["nodejs_compat"]

[[migrations]]
tag = "init"
new_sqlite_classes = ["Cdb", "Catalog", "Gateway", "Resharder"]

[[durable_objects.bindings]]
name = "CDB_CATALOG"
class_name = "Catalog"

[[durable_objects.bindings]]
name = "CDB_SHARD"
class_name = "Cdb"

[[durable_objects.bindings]]
name = "CDB_GATEWAY"
class_name = "Gateway"

[[durable_objects.bindings]]
name = "CDB_RESHARD"
class_name = "Resharder"

[[r2_buckets]]
binding = "CDB_FILES"
bucket_name = "my-chardb-app-files"


[assets]
directory = "public"
binding = "CDB_DASHBOARD"
run_worker_first = ["/_chardb/*", "/api/*", "/health", "/ws"]

[observability.logs]
enabled = true

[observability.traces]
enabled = true
```

Run the packaged check after any Wrangler edit:

```bash
bunx @chardb/core doctor
```

`doctor` accepts `wrangler.toml` and `wrangler.jsonc`. It checks the compatibility settings, exact Durable Object classes and bindings, reserved asset routes, R2 binding required by file columns, and any Vectorize bindings required by vector columns.
