title: "Deploy"

---

The generated project owns the deployment sequence. Copy the environment template and replace every placeholder:

```bash
cp .env.example .env.local
```

`.env.local` needs:

```dotenv
CHARDB_URL=https://my-chardb-app.example.workers.dev
CHARDB_ADMIN_TOKEN=replace-with-32-to-512-byte-secret
BETTER_AUTH_SECRET=replace-with-at-least-32-byte-secret
```

Bun loads that file for the generated scripts. Git ignores it.

## First deployment

```bash
bun run setup:cloudflare
bun run deploy:bootstrap
```

`setup:cloudflare` checks or creates the exact R2 bucket named in `wrangler.toml`.

`deploy:bootstrap` uploads the first Worker, passes both secrets through a temporary mode-0600 file, waits for the exact schema version and digest, and runs the packaged migration command. Rerunning it resumes the same migration identity.

## Later deployments

```bash
bun run typecheck
bun run test
bun run build
bun run deploy
```

Routine deploy refuses a missing Worker. It also refuses to upload if the current Worker package and active migration state disagree.

Keep the old Worker artifact until activation succeeds. A code rollback is safe only when the old artifact understands the active schema version. Schema history only moves forward.
